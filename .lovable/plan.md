# Bulk Dispatch Planning

A planning layer on top of the existing dispatch flow. Admins upload Excel plans; WSP users execute them later through the existing `dispatchMaterials` RPC. Existing dispatch, stock, proof, in-transit, and WD-receive logic is untouched.

## 1. Database (new tables only)

Two new tables — no changes to `stock`, `stock_movements`, `wd_assignments`, or any RPC.

`dispatch_plans`
- `id` uuid PK
- `plan_code` text unique (e.g. `PLAN-2026-001`, generated by sequence)
- `wsp` wsp_code NOT NULL
- `wd_code` text NOT NULL
- `plan_date` date NOT NULL default `current_date`
- `status` enum `dispatch_plan_status` ('pending','executed','cancelled') default 'pending'
- `created_by` uuid, `created_at` timestamptz
- `executed_by` uuid null, `executed_at` timestamptz null
- `dispatch_id` uuid null (link to the resulting `stock_movements.dispatch_id` after execution)

`dispatch_plan_items`
- `id` uuid PK
- `plan_id` uuid FK → dispatch_plans
- `material_code` text NOT NULL
- `planned_qty` int NOT NULL CHECK > 0
- `actual_qty` int null (filled at execution)

Sequence `dispatch_plan_seq` + trigger to generate `PLAN-YYYY-NNN` on insert.

RLS:
- `dispatch_plans` / `dispatch_plan_items`:
  - SELECT: `wsp = current_user_wsp() OR has_role(auth.uid(),'admin')`
  - INSERT: admin OR `wsp_admin` (scoped to their wsp) OR admin global
  - UPDATE: `wsp = current_user_wsp() OR admin` (for executing/cancelling)
- Items inherit via parent-plan EXISTS check.
- GRANTs to `authenticated` + `service_role`.

No new dispatch/stock RPCs. Execution reuses `dispatchMaterials(...)` then writes back `status='executed'`, `dispatch_id`, `executed_*`.

## 2. Upload (Super Admin + WSP Admin)

New route `/admin/bulk-dispatch` (linked from admin nav). Accessible to `admin` and `wsp_admin`.

Excel columns: `WSP | WD Code | Material Code | Quantity`. Parsed via SheetJS (`xlsx`, already used in exports).

Client-side validation per row:
- WSP ∈ allowed WSPs (admin: all; wsp_admin: only their wsp)
- WD exists in `hierarchy_wd`
- `(wd_code, wsp)` exists in `wd_assignments`
- Material exists in `materials`
- Quantity is a positive integer

Show row-level errors in a table; block submission until clean.

Grouping: rows are grouped by `(wsp, wd_code)` → one `dispatch_plan` per group, with N items.

After insert, show summary: plans created, WDs impacted, materials imported, with the generated plan codes.

## 3. WSP Dispatch Queue

On `/wd-issue` (existing dispatch page), add a new section above the form: **Pending Dispatch Plans**. Lists pending plans for the active WSP only (scoped via `useEffectiveWsp`), grouped by plan with WD, plan code, plan date, item count. Each card has an **Open** button.

Empty state when no plans → existing manual flow stays visible as today.

## 4. Execute Planned Dispatch

Clicking **Open** prefills the existing dispatch form:
- WD selector locked to plan's `wd_code`
- Date defaults to today (editable, same rules)
- Line items pre-populated from plan items with `actual_qty = planned_qty`
- Each line shows `Planned: X` next to the qty field; user may edit actual qty (0 cancels the line)
- Existing stock / in-transit validation applies as-is
- Proof upload uses existing `ProofImageUpload`

On submit:
1. Call existing `dispatchMaterials(wd, proof.path, items, date)` — unchanged
2. On success, update `dispatch_plans` → `status='executed'`, `executed_by/at`, `dispatch_id`, and write each item's `actual_qty`
3. Refresh queue

If user navigates away without submitting, plan remains pending.

A small **Cancel plan** action (admin / wsp_admin only) sets status to `cancelled` — no stock effects.

## 5. WSP isolation

All queries filter by `wsp = effectiveWsp`. RLS enforces it server-side. Switching WSP via the Super Admin switcher re-fetches and shows only that WSP's plans. CEVL existing behavior unchanged because we add a new feature, not modify existing ones.
